MY TAKE

Match the runtime to the isolation boundary — never force-fit

Architectural synthesis on when to use Foundry Hosted Agents vs ACA Dynamic Sessions/Sandboxes vs AKS Kata (AKSClaw) vs E2B on Azure VMSS.

✅ Good fit
  • Foundry Hosted Agents: To-B business agents using approved APIs & 1,400+ MCP connectors with minimal infra ops.
  • Durable Functions + ACA Apps: Long-running procurement/finance/approval flows needing external event wait & deterministic replay.
  • ACA Dynamic Sessions / Sandboxes: Ephemeral Hyper-V code execution (`~210ms`) or stateful coding/browser workspaces with pause/resume snapshots.
  • AKS + Kata (`AKSClaw`): Multi-tenant engineering/SRE fleets needing BYO harnesses, shared Skill Marketplace, and 5 hard platform boundaries.
  • E2B on VMSS (`D96as_v7`): AI-native products needing 100K+ concurrent virtual computers at `108ms–132ms` startup.
⛔ Not for
  • Routing unmet control needs to Foundry: Never push a customer who needs custom OS/network/sandbox control into Foundry Hosted Agents just because they lack a dev team (engage CSU/Partner instead).
  • Storing durable state only in Dynamic Sessions: Session local storage is wiped on idle reclamation; always persist checkpoints in Azure HorizonDB or Cosmos DB.
  • Blind CPU scale-in on E2B VMSS: Firecracker consumes HugePages; scaling in without HugePages drain & live migration kills active sandboxes.
  • In-pod LLM keys or inherited user tokens: Never mount static API keys in agent containers or let agents inherit full user tokens.
